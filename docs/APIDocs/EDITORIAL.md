# APIドキュメントの編集・デザイン方針

調査日: 2026年9月10日

この文書はAPIドキュメントを保守する人向けの調査メモです。「AI臭い」という印象を、制作者を判定する方法には使いません。文章やレイアウトの特定の特徴だけで、AIの使用を断定できる根拠は今回の資料からは得られていません。

## 調査から分かったこと

### 文面の長さと探しやすさ

NN/gの2025年の記事は、製品に組み込まれた生成AIの利用調査で、冗長な回答、必要な情報を見つけにくい構成、分かりにくい表現が利用者の負担になったと報告しています。これは調査対象の製品に関する観察で、AIが書く文章すべてに当てはまるという主張ではありません。[Product-Specific GenAI Needs to Write for the Web](https://www.nngroup.com/articles/genai-write-for-the-web/)

簡潔さ、拾い読みしやすさ、宣伝を控えた説明が使いやすさに寄与する点は、生成AI以前のWeb文章の比較研究でも扱われています。LikeXではその知見を編集方針の参考にします。研究中の改善率を、そのまま今回のサイトの改善見込みとして使うことはしません。[Concise, Scannable, and Objective](https://www.nngroup.com/articles/concise-scannable-and-objective-how-to-write-for-the-web/)

### 見た目が似通う問題

Anthropicはフロントエンド生成の解説で、指示が少ない場合に配色・フォント・構成が似通う傾向を説明しています。同記事の独自性や演出に関する提案は、生成例と実務上の経験に基づくもので、色や書体による判定精度を検証した研究ではありません。[Improving frontend design through Skills](https://claude.com/blog/improving-frontend-design-through-skills)

APIドキュメントでは、意外性よりも目的の情報へ移動できることが優先です。白背景や標準フォントを排除する必要はありません。別の目立つ書体、強い色、凝った動きへ一律に置き換えると、同じ問題を別の見た目で繰り返してしまいます。

### 技術文書で優先すること

Googleの技術文書ガイドは、気軽さに寄りすぎない親しみやすい文体、説明的なリンク名、条件を先に示す手順、コード表記の区別などを推奨しています。LikeXでも、宣伝文句より「何を渡すか」「何が返るか」「失敗したらどうなるか」を先に書きます。[Google developer documentation style guide](https://developers.google.com/style/highlights)

見出しは内容の階層を伝え、画像には目的に合う代替テキストを付けます。これらは見た目の好みではなく、内容を利用できる形で提供するための指針です。[W3C: Headings](https://www.w3.org/WAI/tutorials/page-structure/headings/)、[W3C: Informative Images](https://www.w3.org/WAI/tutorials/images/informative/)

本文が横に伸びすぎることは避けます。GOV.UKのレイアウト指針も、長すぎる行を防ぎ、狭い画面から設計することを勧めています。具体的な列幅の数値は英語圏の指針をそのまま日本語に当てはめず、日本語の本文とコードを実画面で確認して決めます。[GOV.UK Design System: Layout](https://design-system.service.gov.uk/styles/layout/)

## このサイトで避けるもの

以下はLikeXの用途に合わせた編集判断です。「AI作成を見分ける特徴の一覧」ではありません。

| 避けたい状態 | 読む人に起きること | 採用する書き方・見た目 |
| --- | --- | --- |
| 「強力」「直感的」「柔軟」だけで機能を説明する | 何ができるか、どう呼ぶかが分からない | API名、引数、返却値、操作例を書く |
| 毎ページに長い導入と同じ結論がある | 同じ説明を何度も飛ばすことになる | 冒頭は機能の目的を1〜2文。詳しい説明は該当箇所に置く |
| すべての段落が同じ長さ・同じ語尾になる | 大事な条件と補足の区別がつきにくい | 手順は番号、比較は表、説明は段落にする |
| 「解き放つ」「新たな可能性」「シームレス」などの宣伝表現 | 契約や制約を探しにくい | 「コピーする」「変更する」「保存する」と具体的に書く |
| あらゆる注意を派手な囲み・絵文字で強調する | 本当に重要な注意が埋もれる | データ喪失や非対応など、判断に必要な箇所だけ強調する |
| 3列の同じカードへすべて押し込む | 機能の関係が見えず、表やコードが窮屈になる | 左に機能一覧、右に本文。APIの比較は横並びの表で示す |
| 大きなキャッチコピーが画面上部を占める | 最初に欲しい利用例までスクロールが必要になる | ページ名、短い説明、利用例またはAPI表を上に置く |
| 装飾用のグラデーション、光彩、浮遊する形、常時アニメーション | 本文から注意がそれる | 細い区切り線、控えめな選択色、必要な操作状態だけ使う |
| 違いのないスクリーンショットを全ページへ付ける | どこを見るべきか分からない | 該当機能を操作した実画面に短い説明を付ける。Coreは画像を無理に置かない |
| 実装されていない例を動く例のように載せる | コピー後の調査・修正が増える | 公開型と照合する。利用側が実装するAPIや保存先はサンプルと明記する |
| 見出しやリンクが「詳細」「こちら」だけになる | 移動先を予測できない | 「保存・編集許可」「形式を選択して貼り付け」など対象を明記する |

## ページの構成

左メニューはExplorer、Spreadsheet、Coreを開閉できる構造にします。各コンポーネントの中で関連操作をまとめ、関数名をばらばらに並べるだけの索引にしません。例えばコピー・切り取り・貼り付けは同じページ、タブの追加・移動・分離は同じページに置きます。

本文は、機能の説明、API、利用例、必要な制約を基本とします。ページごとに情報量は変えて構いません。書式設定なら実画面、コールバックなら受け渡す型、ZIPならサイズとパスの制約が中心になります。同じ数の段落や表へそろえる必要はありません。

ページ内の見出しと左メニューの選択状態を一致させます。コード・表は必要な場合だけ横スクロールさせ、本文を画面外へ押し出さないようにします。画像は縦横比を保ち、拡大して読めるようにします。

## 公開前の確認

- API名、必須・任意、既定値、戻り値が公開型と一致している。
- 例の中の変数や利用側APIが説明されている。
- 関連する操作が同じページか、分かる名前のリンクでつながっている。
- スクリーンショットが実装済みの画面と一致し、何を示す画像か説明されている。
- キーボードで左メニューを開閉し、各ページへ移動できる。
- 狭い画面でも本文、表、コードを読める。
- 見出し、余白、文字色の差だけで情報の優先順位が分かる。

「人が書いたように見せること」より、機能を探し、実装へ使えることを確認します。
