# セキュリティ診断・修正記録（2026-10-25）

対象はCore、Explorer、Spreadsheet、LikeDocument、LikeSlideと、それらをビルド・検証する依存パッケージです。`e38a3e9` を基点とする作業ツリーで診断しました。診断開始前から存在するソースコピー導入の変更は保持しており、この記録の修正件数には含めません。

不正なOffice/XML/JSON、クリップボード、検索・置換、数式、画像・リンク、閲覧許可の変更を入力境界として確認しました。今回確認した問題の中心は、入力サイズの上限内でもCPU時間や出力メモリが膨らむ処理と、プレビュー表示中の権限変更です。

## 修正した問題

### Core：不正XMLによる処理時間の増大

XML実体参照の旧正規表現は、`;` のない `&` が連続すると残りの文字列を繰り返し探索していました。例外を投げるコールバックに到達する前に探索が進むため、XMLのサイズ制限だけでは長時間の処理を防げませんでした。XLSX・PPTX・DOCXなど、共通XMLリーダーを利用する経路に影響します。

前方への走査で最初の不正実体を拒否する共通デコーダーへ置き換え、通常版・ストリーム版の両方から使用します。参考実測では、連続する `&` 40,000文字が修正前約2.3秒、修正後1ミリ秒未満でした。計測値は環境依存です。

- 実装：`packages/core/src/ooxml/xml-entities.ts`、`xml.ts`、`xml-stream.ts`
- 回帰確認：`packages/core/tests/ooxml-xml-stream.test.mjs`。100万文字の不正入力を隔離ワーカーで確認し、通常の名前付き・数値実体参照も確認。

### Core・Spreadsheet：置換結果のメモリ増幅

短い検索文字列に長い置換文字列を指定すると、入力がそれぞれの制限内でも巨大な結果を作成できました。生成後の検証では割り当てを防げません。

`TextSearchMatcher.replace(text, replacement, maxOutputLength?)` に出力上限を追加しました。既定は16,777,216 UTF-16コード単位で、超過する断片を追加する前に `RangeError` を投げます。Spreadsheetはセル上限100,000を明示的に渡します。照合結果を先に全件配列へ展開する処理も避けます。

- 回帰確認：`packages/core/tests/text-search.test.mjs`、`packages/spreadsheet/tests/security-inputs.test.mjs`。100億文字相当になる置換の拒否、Unicode・ゼロ幅マッチ、置換失敗時の一括操作の原子性。
- 互換性：既定上限より大きい結果が必要なCore利用側は、第3引数に上限を明示できます。`$1`・`$&` は従来どおりリテラルです。

### Spreadsheet：TRIM・連番フィルの正規表現による処理時間の増大

`TRIM` の末尾空白除去とフィルの数値接尾辞判定に、長い入力で探索を繰り返す正規表現がありました。100,000文字以内のセルで再現し、参考実測ではTRIMが約14.5秒、50,000文字のフィルが約3.6秒でした。

TRIMは先にASCII空白の連続を縮約し、フィルは末尾から数字を走査する処理へ変更しました。通常の空白、符号、連番、先頭ゼロの扱いを回帰確認しています。

- 実装：`packages/spreadsheet/src/model/formula-functions/text.ts`、`model/editing/fill.ts`
- 回帰確認：`packages/spreadsheet/tests/security-inputs.test.mjs`。公開コマンド・数式評価を隔離ワーカーで実行。

### Spreadsheet：クリップボードを全文デコードする前の上限

プレーンテキストはBlobサイズを確認してからデコードし、デコード後も10 Mi文字の上限を確認します。内部コピー識別子のためだけにHTML全文を読む処理は、先頭64 KiBに限定しました。識別子の長さも制限します。HTMLを実行・挿入する変更ではありません。

- 実装：`packages/spreadsheet/src/state/clipboard/browser-clipboard.ts`
- 互換性：先頭64 KiBより後にある内部コピー識別子は認識せず、プレーンテキストとして扱います。
- 回帰確認：巨大Blobの全文読み込みが呼ばれないこと、`read` / `readText` 双方の上限、通常の内部コピー。

### LikeSlide：アニメーションの展開量・変換量

小さなPPTXから大量の繰り返しノードを生成でき、また共有されたアニメーション木を正規化する際に入力より大きな木を複製できました。入力ファイルの容量上限だけでは防げません。

デッキ全体の展開ノード数を100,000までに制限し、繰り返しの乗算と共有木の展開を生成前に検証します。さらに、PPTX変換で繰り返す比較・サンプリング処理を資料全体10,000,000単位までに制限します。正規モデルの大きな繰り返し回数自体は、実体ノードを増やさない場合に維持します。

PPTXの限度を超えたアニメーションは `animation-limit` 診断付きで省略し、処理可能な部分を維持します。ネイティブJSON・モデル操作は上限違反を拒否し、部分適用しません。

- 実装：`packages/slide/src/model/animation-budget.ts`、`animation-validation.ts`、`normalize.ts`、`import/pptx-animations.ts`、`pptx-reader.ts`
- 回帰確認：`packages/slide/tests/animation-budget.test.mjs`、`slide-animations.test.mjs`、`pptx-animation-resilience.test.mjs`。巨大な繰り返し、共有木、ページをまたぐ合計、上限境界、通常のアニメーションの維持。
- 互換性：従来通っていた極端に大きい展開は拒否・省略対象になります。公開型・保存形式のバージョンは変更していません。

### Explorer：閲覧許可を取り消したプレビューが残る

ファイルを開いた後に `getEntryPermissions` が閲覧を拒否しても、すでに開いているプレビューが残りました。現在のレンダーに渡されたポリシーで再判定し、拒否・判定例外時にはプレビューをアンマウントします。許可を戻しても自動では開き直しません。

主画面と別ウィンドウの両方で、親フォルダから継承した拒否と、同じコールバックの判定結果変更を確認しました。利用側は許可変更時にReactの再レンダーを起こす必要があります。外部へ開いた独自プレビューとサーバー側の認可は利用側の責務です。

- 実装：`packages/explorer/src/state/use-explorer-controller.ts`
- 回帰確認：`packages/explorer/tests/explorer-entry-permission-views.test.mjs`。修正前の失敗を確認してから修正。

## PDF追加対応：展開量・処理量を制限したページ数検査

以前の内蔵検査は `pdf-lib` で文書全体を読み込んだ後にページツリーを検証していました。小さな圧縮ストリームから巨大なデータが展開される場合、後段の上限に到達する前にメモリ・CPUを消費し、同期的な展開中には中止・タイムアウトも処理できませんでした。

必要な参照テーブル・オブジェクトストリーム・ページツリーだけを読む検査へ置き換えました。本文・画像・フォントは展開せず、各段階のサイズを確認してからデータを保持します。Flateには `pako@3.0.2` の低水準APIを使い、圧縮入力1 KiB・出力16 KiBずつ処理します。構文解析・他フィルター・予測処理も処理量に応じてイベントループへ制御を返し、キャンセル・30秒のタイムアウト時に実際の解析を止めます。

主な上限は入力100 MiB、メタデータ1ストリームの入力・各展開段階16 MiB、全段階の展開量合計64 MiB、参照テーブル・圧縮オブジェクト・ページツリー各100,000件、生成する値600,000個、総処理量256 Mi単位です。間接参照の共有グラフを復号パラメータへ展開するときも、コピーされる値ごとに上限へ計上します。これは元ファイルやJSオブジェクト等を含むプロセス全体のメモリ上限ではありません。

通常・圧縮・混在参照テーブル、追記更新、削除済み参照、世代番号、圧縮オブジェクト、間接Lengthに対応し、実際のページ数とCountを照合します。メタデータにFlate・LZW・ASCIIHex・ASCII85・RunLength、TIFF/PNG予測処理を使用できます。未対応のフィルター、暗号化、循環、不整合、上限超過、最初の参照ストリームの未解決の間接Lengthは拒否します。破損ファイルの修復や上限のないパーサーへの自動切り替えは行いません。必要な場合は既存の `upload.inspectFile` でホスト側の検査へ差し替えられます。

PDF解析上限は `upload.pdfInspectionLimits` と単独検査API `inspectExplorerUploadFile` の `request.pdfInspectionLimits` から個別に変更できます。既定値は維持し、参照テーブル件数・圧縮オブジェクト件数・ページツリー件数は独立した項目にしました。設定は検証・コピーして保持し、PDFの解析上限変更時は成功・失敗のキャッシュを再利用せず再検査します。

- 実装：`packages/explorer/src/inspection/pdf*.ts`
- 回帰確認：独立したPDFバイト列で構成した公開APIテスト19件、フィルターの展開量・整合性・中止テスト11件、上限設定の解析テスト7件、公開API・キャッシュ・処理中のGUI設定変更テスト10件。既存の `pdf-lib` 生成PDFの検査も継続して成功。
- 対応範囲：[内容検査の制限](../packages/explorer/src/docs/upload-content-limits.md)。PDF全体の表示互換性や、本文・添付ファイル・JavaScriptの無害性を保証する検査ではありません。
- 仕様参照：[PDF 1.7 / ISO 32000-1](https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/PDF32000_2008.pdf)、[Pako公式ソース](https://github.com/nodeca/pako)。

LikeDocumentでは今回新たに確定した固有の脆弱性はありませんでした。共通CoreのXML修正がDOCX読み込みにも適用され、Documentのテストで互換性を確認しています。直接のHTML挿入、画像・リンクの許可処理、モデル正規化、OfficeのZIP/XML境界もレビューしましたが、問題が存在しないことを保証するものではありません。

構造と信頼境界の確認記録は [audit-context/DOSSIER.md](../audit-context/DOSSIER.md) にあります。手動レビュー・テスト・公開アドバイザリは有限の確認であり、未知の問題、ホストアプリの認証・保存処理、ブラウザ内部のデコーダー、未確認環境を網羅するものではありません。
